> 技术栈：Vue 2 + @stomp/stompjs@6 + RabbitMQ（STOMP 插件）+ SaaS 多门店 POS \
> 关键词：WebSocket 连接治理、指数退避、影子双发、运行时灰度

我负责的收银台是一款 SaaS 多门店 POS：每台收银机启动后要通过 STOMP over WebSocket 订阅若干类实时推送——桌台变更、营销活动、自助餐退押金、订单状态、叫号。过去这是 3 条独立连接、各自为政的固定间隔重连。MQ 高峰期，它演变成一场所有门店同时参与的重连风暴。

这篇文章复盘两期治理（Phase A 单连接合并、Phase B 统一交换机）的设计取舍、三代灰度方案的演进，以及一路踩过的坑。文中交换机名、接口名等已做脱敏处理。

## TL;DR

- **Phase A**：3 条业务 WebSocket 合并为 1 条共享连接（注册表模式 + 指数退避 + 抖动），重连从 500ms 固定间隔变为 5s~35s 随机退避。
- **Phase B**：后端新增统一交换机 `shop.pos.unified.topic`，前端一个目的地收全部业务，按消息体 `exchange_type` 路由到原有 handler，业务逻辑零改动。
- **灰度三代演进**：构建期四态开关 → 构建期烙 SN 名单（每次灰度都要发版）→ 店铺信息接口返回运行时字段（灰度零发版）。最后一跳把「谁控制放量」从构建期挪到运行期，是整个项目里 ROI 最高的一次重构。
- **核心取舍**：共享连接把爆炸半径从「单业务」扩大到「全部业务」——未声明交换机的订阅会收到 ERROR 帧断掉整条连接。这个代价靠灰度纪律兜住。

## 一、背景：一场自己制造的重连风暴

治理前的形态是三个历史时期叠加的产物，每个模块各自 `new Client()`：

| 模块 | 业务 | 重连策略 |
| --- | --- | --- |
| stomp.js | 桌台 / 活动 / 自助餐（后续又挂了临期提醒） | 60s 固定间隔 |
| orderStomp.js | 订单 | **500ms 固定间隔** |
| numberCallingStomp.js | 叫号 | 固定间隔 |

问题在高峰期集中爆发：

1. **同步重试风暴**。MQ 或网络抖动时，所有门店的所有 POS 同时进入重连。订单连接 500ms 一试，意味着一台机器每秒对 broker 发起 2 次连接握手，门店规模上去之后这个乘法就是灾难——broker 越忙越拒连，越拒连客户端越拼命重试，正反馈放大。
2. **固定间隔没有退避**。失败 1 次和失败 100 次的重试节奏完全一样，既打不满恢复窗口，又持续供给压力。
3. **连接数随业务膨胀**。每次新业务（自助餐、临期提醒）都往现有连接上挂新订阅，订阅数在涨，但架构上从未回答「连接数能不能降」。

## 二、目标与非目标

**目标**：连接数 3 → 1 且新业务接入不再增加连接；重连具备指数退避 + 随机抖动，从机制上消除同步风暴；**业务逻辑零变化**（5 类推送的消息处理一行不改）；可灰度、可回滚，单店粒度可控。

**非目标**：不改后端推送逻辑（Phase B 才动后端，且只加不改）；不做连接断开语义优化（桌台类订阅本来就是应用生命周期级，永不注销）；不处理跨标签页共享连接（收银机是单实例单页运行，没有多标签复用连接的场景，SharedWorker 之类不在考虑范围）。

「业务逻辑零变化」是这次治理最重要的自我约束：**迁移和重构不混做**。所有旧订阅回调逐字提取为新函数，迁移 PR 里凡是消息处理相关的 diff，审查标准都是「必须与原逻辑逐字一致」。

## 三、Phase A：三条连接合并成一条

### 3.1 注册表模式

ConnectionManager 是一个单例，核心是一张注册表：

```js
// destination -> { handler, subscription }
const registry = new Map()

export function register(destination, handler) {
  const existing = registry.get(destination)
  if (existing) {
    existing.handler = handler   // 仅覆盖 handler，不重发 SUBSCRIBE
    return
  }
  const entry = { handler, subscription: null }
  registry.set(destination, entry)
  if (client && client.connected) {
    subscribeEntry(client, destination, entry)  // 晚到的立即补订
  }
}
```

三个业务模块不再持有自己的 Client，改为把自己的 destination 注册进来。订阅回调经注册表**间接派发**——subscribe 闭包里每次都从 `registry.get(destination)` 取最新 handler。这个间接层换来一个关键性质：**运行中覆盖 handler 不需要重发 SUBSCRIBE 帧，不存在漏消息窗口**。

生命周期用引用计数语义：`unregister` 注销单个目的地，注册表清空才真正 `deactivate` 断开共享连接。实际上桌台类订阅永不注销，所以这条连接存活整个应用生命周期——与治理前现状一致，没有引入新的生命周期问题。

### 3.2 重连：指数退避 + 抖动

```text
delay(n) = min(30000, 5000 · 2^n) + rand(0, 5000)
```

基数 5s、上限 30s、抖动上限 5s。抖动不是可选项：没有它，退避只是把「每 500ms 一试」变成「每 30s 一次集体冲锋」——所有客户端仍然同步。抖动把同步峰值摊成均匀噪声，这才是消除风暴的那一半。

另一个细节：**只有被动断开才计入失败**。

```js
onWebSocketClose: function() {
  if (client && client.active) {
    consecutiveFailures += 1   // 主动 deactivate 不计，下次激活首连不退避
  }
}
```

主动关停（登出、清订阅）后重开连接不该被惩罚性等待；这个区分靠 stompjs 暴露的 `active` 状态判断。

### 3.3 stompjs v6 的三个坑

项目锁在 `@stomp/stompjs@6.1.2`，文档上很多「理所当然」的写法在 v6 里不成立：

**坑 1：v6 不支持函数式 `reconnectDelay`**——那是 v7 API。但 v6 的自动重连要求 `reconnectDelay > 0` 才会持续重试，于是用了一个组合技：`reconnectDelay` 设为 1ms（仅作为调度 tick），真实退避放在 `beforeConnect` 钩子里 `await sleep(delay)`。这个钩子每次连接尝试（含自动重连）前都会被 await，且 v6 在 await 返回后会复查连接状态——等待期间主动关停不会产生孤儿连接。这是翻源码确认过的行为，不是文档承诺。也要提醒：**这套组合技的行为契约来自 6.1.2 的实现细节**，目前靠锁版本钉住；将来升 v7（原生支持函数式 `reconnectDelay`）时，第一件事就是重验这条链路，理想情况是为它补一个基于假定时器的回归测试。

**坑 2：跨会话 unsubscribe 是断连炸弹**。重连成功 = 全新的 STOMP 会话，旧会话的订阅句柄全部失效。直觉写法是重连后把旧 subscription 逐个 `unsubscribe()`——但向新会话发送过期订阅 id 会触发服务端 ERROR 帧，直接断连。正确做法是**刻意不清理旧句柄**，直接置空重建：

```js
onConnect: function() {
  // 重连 = 新 STOMP 会话，旧订阅句柄已失效；不对其调用 unsubscribe
  // （向新会话发送过期 id 会触发服务端 ERROR 帧断连），直接置空重建
  registry.forEach(function(entry, destination) {
    entry.subscription = null
    subscribeEntry(client, destination, entry)
  })
}
```

**坑 3：DEACTIVATING 状态下 `activate()` 会 throw**。收尾中的连接不能直接重新激活，`ensureActive` 里挂了一个 `deactivatePromise`，等收尾完成再按需激活。

### 3.4 心跳

双向心跳 4s。注意 STOMP 心跳是**协商值**，双方取较大者，所以客户端设 4s 只能保证「不比 4s 更稀疏」——它的意义是让死连接（半开 TCP）在秒级被探测到，而不是等 nginx/防火墙的空闲超时来掐。

## 四、Phase B：统一交换机

Phase A 把 3 条连接合成 1 条，但旧链路每个业务仍是一个独立目的地（当时 5 个：桌台/活动/自助餐/订单/叫号），后端要维护 5 条推送链路，前端要维护 5 个订阅注册。Phase B 在后端加了一个统一交换机做**影子双发**：

```text
旧链路:  order.exchange / shop.table.topic / shop.platformActivity.topic
         / shop.buffetOrder.topic / shop.numberCalling.topic     （照常投递）
统一链路: shop.pos.unified.topic，routing key: {sn}.{biz}...     （照常投递）
         订阅: /exchange/shop.pos.unified.topic/{sn}.#
```

前端在灰度名单内只注册统一订阅这一个目的地，5 类业务从一个 destination 进来，按业务分发。

### 4.1 路由：权威字段 + 双层兜底

统一交换机引入了一个新的分发维度问题：一个 destination 进来的消息，怎么知道是哪个业务？后端在推送消息体里加了 `exchange_type` 字段作为**权威业务标识**，前端的分发是三层兜底：

```js
function shopPosUnifiedHandler(message) {
  // 权威依据优先：消息体 exchange_type；兜底：rk 第二段（过渡期后端漏发字段时不丢消息）
  const biz = parseExchangeType(message.body)
    || parseShopPosUnifiedBiz((message.headers || {}).destination)
  const handler = EXCHANGE_TYPE_HANDLERS[biz]
    || (isExpiryRemindEvent(message.body) ? expiryRemindTopicHandler : null)
  if (!handler) {
    console.warn(`无法识别的业务类型(${biz})，消息丢弃`)
    return
  }
  handler(message)
}
```

三个设计点：

1. **`exchange_type` 优先于 routing key 解析**。rk 第二段（`{sn}.table.{tableId}` → `table`）曾是唯一依据，但 rk 是路由语义、`exchange_type` 是业务语义，后者由后端显式声明，跨环境更稳。rk 兜底保留是因为过渡期后端可能漏发字段，不能因此丢消息。
2. **未知业务 warn + 丢弃，而不是抛错**。后端已定义电子菜单业务但 POS 无消费方，走这条路丢弃。这保证了后端新增业务时前端「不炸」——补一行路由映射即可接入。唯一的缺口在可观测性：收银机上没人开着 console，这条 warn 目前没有接上报，属于待补的信号（见第九节）。
3. **临期提醒是第三层兜底的实例**。旧链路该业务仅靠消息体 `event` 字段区分，没有独立的 `exchange_type` 声明，于是统一链路里用 `event === 'expiry_remind'` 兜底识别，保持与旧链路相同的判断方式。

### 4.2 单链路互斥

灰度期间同一门店同时存在两条可达链路（后端双发），但**前端单店同一时刻只注册一条**：

```js
// 每个旧模块的 init 里：
if (shouldConsumeShopPosUnified(shopInfo)) {
  return   // 统一链路已覆盖本店，旧订阅不注册
}
```

这是理解整个灰度安全性的关键，把两条不变量拆开看：

- **后端影子双发** → 任意时刻每条消息在旧链路上始终存在。无论前端注册了哪条链路，数据都有一个可达的来源——这是「不丢」的来源；
- **前端单链路注册** → 任何一家店同一时刻至多消费一条链路，永远不可能双收——这是「不重」的来源。

两条不变量合起来，错配窗口的残余风险只剩一个已知方向：**前端已切统一链路、后端对该店的双发尚未生效**（字段生效存在时差），表现为短时静默漏发——这正是第六节「每批放量后真实推送验证」要兜住的情形。至于「重复消费」，它只存在于第一代灰度的 `dual` 模式里：那个模式存在的意义就是实测「双收无害」，结论拿到手后随单链路互斥策略一起退役。

### 4.3 与旧链路的逐字对齐

统一链路的 order/calling 原始 handler 与旧模块的解析逻辑逐字一致（同样的 try-catch 边界、同样的错误日志文案），桌台/活动/自助餐/临期则直接复用旧 handler 函数。分发的下游（消息分发入口、各 callbacks 数组）完全不变——业务组件对链路切换无感知。

## 五、灰度控制的三代演进

这个项目最有意思的部分不是连接合并，而是「怎么安全放量」这件事被推翻重来了三次。

**第一代：构建期四态开关**。`MQ_SHOP_POS_UNIFIED` 环境键：`off`（不注册，初始默认）/ `dual`（双订阅，验证双消费用，后随单链路互斥策略废弃）/ `whitelist`（按名单自选）/ `only`（全量切换期）。

**第二代：构建期 SN 名单**。名单烙进构建产物，问题立刻暴露：**每加一批门店都要前端重新构建发版**。还形成了协作不变量「前端名单 ⊆ 后端名单」——加名单后端先行、前端后发版，摘名单对称。流程能跑，但每次放量都是一个完整发版动作，且非 whitelist 构建里名单是死数据。

**第三代：运行时字段（现行方案）**。后端在登录态拉取店铺信息的接口（前端封装为 `getInfo`，结果整体写入全局 store）返回里加了一个字段：

```jsonc
{ "unified_push": 1 }   // 1 = 该店参与影子双发，走统一链路；0/缺失 = 仅旧链路
```

前端判定收敛为一个函数，成为链路判定的**唯一接缝**：

```js
export function shouldConsumeShopPosUnified(shopInfo) {
  const mode = process.env.MQ_SHOP_POS_UNIFIED
  if (mode === 'only') {
    return true                              // 全量强制（构建期）
  }
  if (mode === 'whitelist') {
    return Number((shopInfo || {}).unified_push) === 1   // 运行时逐店判定
  }
  return false
}
```

效果：**前端所有门店装同一个包，每家店启动/重登时按自己的 `unified_push` 自选链路**。灰度 = 后端改字段，下次登录生效，前端零发版。第二代那套「名单协作不变量 + 发版排期」整体退役，判定模块从 40 行名单管理缩成 10 行纯判定——整个改造合计 37 增 / 65 删，净删 28 行（对账见第八节）。`Number(...)` 归一化是防御性细节：字段可能以字符串 `'1'` 到达，`=== 1` 会漏判。

**这一跳的普适教训**：把「谁控制放量」从构建期挪到运行期，灰度成本从「一个发版周期」降到「一次配置变更」。凡是灰度开关，都值得先问一句——这个开关的值，真的需要由构建产物决定吗？

**环境矩阵（现状）**：5 个构建环境全部 `whitelist` 态，具体门店由运行时字段决定。回滚两档：单店回退 = 后端把该店字段改回 0；整体回退 = 发 `off` 包（三连接的 multi 形态已删，不存在更深的回退）。

## 六、共享连接的代价：爆炸半径

合并连接不是免费的。旧形态下，叫号订阅出错只影响叫号；共享连接后，**一个订阅的问题会断掉全部业务**。最大的风险点是 RabbitMQ 的原生语义：**订阅一个未声明的交换机，服务端会回 ERROR 帧并断开连接**——整条共享连接上所有订阅一起陪葬。

所以 Phase B 有一条硬前提：**目标环境的后端必须已声明统一交换机**。这也是 `MQ_SHOP_POS_UNIFIED` 长期默认 `off` 的原因——off 包在任何环境都物理安全。

另一层错配语义则友好得多：后端确认过，**名单错配（前端订阅了、后端没给这家店双发）是静默不投递**——无 ERROR 帧、不断连，消息只是不来。这很安全，但安全得可怕：**静默故障没有信号**。由此定下一条放量纪律：每批门店切换后，必须在真实门店触发一次真实推送做端到端验证，不能只看「连接正常」。

共享连接还带来一个已知取舍：换店重登后，旧 SN 的统一订阅不会主动注销。代价是 broker 上多挂一个无效订阅——好在 `/exchange/` 目的地的订阅由 STOMP 插件创建的是临时 auto-delete 队列，连接断开即自动清理，这份残留是有界的（最长存活到这条共享连接下一次断开为止）；收益是省掉整套注销时序。评估后保留原设计。

## 七、验证纪律

两期上线的验证都是人工逐项过的：

1. **帧级验证**：开发者工具直接看 WS 帧内容，确认统一链路每类业务的 `exchange_type`、rk 格式、消息体结构与旧链路一致；
2. **业务级验证**：两类形态（灰度店 = 单连接单统一订阅；非灰度店 = 旧订阅集）下，全部业务功能逐项人工触发；
3. **守卫时序验证**：链路判定依赖 store 里的店铺信息，必须确认路由守卫先 `await getInfo` 再进 Layout（Layout 挂载时才初始化订阅）——这是「订阅初始化读 store」模式的前提，时序错了判定永远拿到空对象；
4. **每批放量后的真实推送触发**（见上节）。

## 八、收益

| 指标 | 治理前 | 治理后 |
| --- | --- | --- |
| 每台 POS 业务 WebSocket | 3 条 | 1 条 |
| 重连策略 | 500ms / 60s 固定间隔 | 5s~35s 指数退避 + 抖动 |
| 高峰期重连时序 | 所有门店同步冲锋 | 抖动摊成均匀噪声，门店间错峰 |
| 新业务接入成本 | 挂新订阅 | 旧链路 + 统一链路各加一个 handler |
| 灰度一批门店的成本 | 前端发版 | 后端改字段 |

连接数 3→1 意味着 broker 侧来自 POS 的连接数直接砍到三分之一（全量升级完成后；灰度期按门店比例过渡）；退避 + 抖动意味着高峰期不再有同步重试峰。Phase A 主提交 547 增 / 272 删（14 个文件），第三代灰度改造 37 增 / 65 删（即第五节「净删 28 行」的出处）——越接近终态，代码越少。

还有一个隐含收益在临期提醒业务上得到验证：治理后新增的业务，接入方式是旧链路加一个目的地、统一链路路由表加一行映射，两个 PR 都没有触碰 ConnectionManager 一行代码。**基础设施改造成功的标志，是后续业务感觉不到它的存在。**

## 九、还没做完的事

- 全量切 `only` 后，删除旧订阅模块的注册代码（后端停投旧链路之后）；
- 旧链路寻址混用 shopId 与 SN（桌台类用 shopId、订单用 SN），统一链路已归一到 `{sn}.#`，旧链路不回头清理；
- 静默不投递的恢复路径依赖拦截层级（投递层拦截 = 加名单后自愈；订阅层拦截 = 需刷新重登），待后端钉死后补对应的恢复逻辑；
- **可观测性欠账**：未知业务丢弃目前只有 `console.warn`（收银机上没人看 console），静默漏发的端到端验证还是人工触发——两者都值得接上报 / 自动化巡检；
- **退避组合技缺回归测试**：3.3 坑 1 的行为契约来自 stompjs 6.1.2 的实现细节，目前靠锁版本钉住，值得用假定时器补一个回归测试，也给将来升 v7 铺路。

## 结语

回头看，这次治理真正值得沉淀的是三个决策模式：

1. **迁移与重构不混做**——所有消息处理逻辑逐字搬迁，审查标准是「diff 必须为零语义变化」，这让排障空间始终只有一维（新架构），而不是两维（新架构 × 改过的业务逻辑）。
2. **错配要收敛到无害**——后端双发 + 前端单链路，把灰度期名单错配的故障面收敛到「永不双收、旧链路兜底不丢」，唯一残余的静默漏发窗口交给真实推送验证兜住，灰度才敢快。
3. **运行时优先于构建期**——灰度开关的终态应该在运行时数据里，而不是构建产物里。发版是最贵的运营动作，能不用就不用。
